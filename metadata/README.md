# Metadata

Links from each composition to external catalogues. This folder is **not**
part of the annotated dataset: it is a convenience layer that lets the corpus
be connected to recordings and to other datasets.

The code that produced these files (`scripts/metadata_pipeline.py`) was written
with the assistance of generative AI, and is based on the pipeline in
[stefan-balke/mpb-corpus](https://github.com/stefan-balke/mpb-corpus).

**Status: the external identifiers here are provisional and have not been
reviewed by a human.** Please read *How far to trust this* below before citing
any of them.

Everything is comma-delimited, UTF-8 without BOM, LF line endings — the same
contract as `dataset_by_corpus/`.

## Files

| file | rows | what it is |
|---|---|---|
| `corpora.csv` | 10 | the composers and their Spotify playlists — **hand-authored**, the only seed here |
| `compositions.csv` | 500 | one row per composition, with every external identifier |
| `musicbrainz_isrc_lookups.csv` | 482 | cache of what MusicBrainz returned per ISRC |

Everything except `corpora.csv` is generated by
`scripts/metadata_pipeline.py`. **Edits made by hand are destroyed by the next
run**, so corrections belong upstream, in the dataset or in `corpora.csv`.

`musicbrainz_isrc_lookups.csv` is a pipeline cache rather than published data,
but it is worth reading for one thing: it lists every recording and work
MusicBrainz returned, where `compositions.csv` only counts them.

## Columns of `compositions.csv`

**Identity**, rebuilt from `dataset_by_corpus/` by the `build` command:

| column | meaning |
|---|---|
| `corpus_id`, `composition_id` | the composition's identity in the corpus |
| `composition_name` | its name, as in the dataset |
| `has_note_function` | whether note-function data exists for it |

**Spotify**, from the `spotify` command:

| column | meaning |
|---|---|
| `spotify_track_id` | the matched track |
| `spotify_track_title`, `spotify_track_artist`, `spotify_duration_ms` | as Spotify reports them |
| `spotify_match_status` | `exact`, `normalized`, `fuzzy` or `unmatched` |

**ISRC**, from the `isrc` command: `isrc`, the ISO 3901 code identifying the
*recording*. Unlike a Spotify id it is platform-independent and outlives any
one service.

**MusicBrainz**, from the `mbisrc` command:

| column | meaning |
|---|---|
| `musicbrainz_recording_count` | recordings MusicBrainz holds for this ISRC |
| `musicbrainz_recording_id` | written **only** when that count is 1 |
| `musicbrainz_work_count` | distinct works those recordings point to |
| `musicbrainz_work_id` | written **only** when that count is 1 |
| `musicbrainz_work_title` | the work's title, so the id can be read |
| `musicbrainz_match_status` | see below |

An identifier is never chosen from among several candidates. An empty
`musicbrainz_recording_id` beside a count of 7 says *MusicBrainz holds seven
recordings for this code*, which is a different statement from *nothing was
found* — and the two would be indistinguishable if only the id were recorded.

## Current status

### Spotify matching

```
exact 428   normalized 34   fuzzy 20   unmatched 18
```

482 of 500 compositions carry a track id, and no track is assigned twice.

### ISRC

All 482 matched tracks returned an ISRC — complete coverage on the Spotify
side. No ISRC is shared by two compositions, which is the check that would
have exposed the matcher selecting one recording twice.

### MusicBrainz

```
one_recording 156   several_recordings 69   isrc_not_in_mb 257   no_isrc 18
```

| status | meaning |
|---|---|
| `one_recording` | exactly one recording carries this ISRC — recording id recorded |
| `several_recordings` | MusicBrainz holds more than one, usually duplicate entries for the same composition — no recording id recorded, but the work id is when they share one |
| `isrc_not_in_mb` | MusicBrainz does not hold this ISRC |
| `no_isrc` | the composition has no Spotify match, so no ISRC to look up |

**198 of 500 compositions (40%) carry a MusicBrainz identifier** — 156
recording ids, 119 work ids, 77 both.

MusicBrainz knows 225 of the 482 ISRCs, so its coverage of this repertoire is
about 45%. That is the ceiling on this approach, and finishing nothing further
will raise it: the remaining codes are simply absent from MusicBrainz.

**Coverage is very uneven between composers**, and this matters for any
analysis:

| corpus | ISRCs | recording ids | work ids |
|---|---|---|---|
| CHICO | 50 | 36 | 31 |
| DJAVAN | 49 | 21 | 24 |
| MILTON | 49 | 21 | 17 |
| JOBIM | 46 | 20 | 19 |
| CAETANO | 49 | 14 | 9 |
| RITA | 50 | 13 | 7 |
| BOSCO | 49 | 9 | 3 |
| EDU | 47 | 9 | 5 |
| GIL | 48 | 7 | 4 |
| LINS | 45 | 6 | **0** |

This reflects how thoroughly each composer has been catalogued by MusicBrainz
editors, not anything musical. **The MusicBrainz columns are not a uniform
sample**, and grouping by composer would be confounded by editorial coverage.
Ivan Lins has no work identifiers at all.

## How far to trust this

**None of these identifiers has been reviewed by a human.**

The Spotify match compares *titles only*. It cannot establish that the selected
recording, release or version is the intended one -- 17 of the matched tracks
are live versions, remasters or medleys. A `fuzzy` or `normalized` status means
the titles did not even agree exactly, and several of those point at spelling
errors in `composition_name` rather than at matching failures.

The MusicBrainz columns are more cautious by construction: they record how
certain the answer is instead of only what was found, and an identifier appears
only where nothing had to be guessed.

## How the MusicBrainz identifiers were obtained

By ISRC lookup: `GET /ws/2/isrc/{isrc}` asks MusicBrainz directly for the
recordings carrying a given code. It is a lookup rather than a search, so
nothing is scored and no threshold is applied. Works are read from the
recordings' relations, and are recorded alongside them because the corpus
encodes *compositions*: where MusicBrainz holds several duplicate recordings,
the work often remains unambiguous.
